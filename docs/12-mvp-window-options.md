# 12. MVP "별도의 창" 운영 방안 비교

## Context

`TriAgent_SMB`는 Nous Research **Hermes Agent CLI** 위에 구성된 SMB(카페/음식점/미용실/편의점) AX 자동화 설정 프로젝트다. 자체 React/Electron 프론트엔드는 없고, 대시보드는 Hermes Agent CLI에 내장된 기능을 `docker-compose`로 띄워 `http://127.0.0.1:9128`에서 서비스한다 ([docker-compose.yml](../docker-compose.yml), [08-docker-deployment.md](08-docker-deployment.md)). 코디네이터 1개 + 워커 프로필 6개(주문결제/재고/예약/CS/매출분석/마케팅-CRM), HITL 승인 게이트 3곳, Mock POS(FastAPI)가 구성 요소다.

이 저장소가 위치한 `e:/work/Hermes/` 아래에는 이미 `HermesSMBStaff`, `TriAgent_MICE`, `TriAgent_Planner` 등 형제 프로젝트가 각자 포트를 나눠 쓰며 동시에 떠 있다. 사용자는 "본 서비스"(TriAgent_SMB)를 MVP로 구성해 **별도의 창(window)** 으로 운영하고 싶어 하는데, 이 저장소에는 "창"이라는 개념 자체가 코드로 존재하지 않는다(Electron/멀티탭/멀티인스턴스 코드 없음). 따라서 "별도의 창"이 의미할 수 있는 세 가지 현실적 해석을 비교 정리한다 — 사용자가 각각의 비용/효과를 보고 방향을 고를 수 있도록 하는 것이 이 문서의 목적이며, 아직 구현 방향은 확정되지 않았다.

## 비교 대상 3가지 옵션

### 옵션 A — 독립 배포 인스턴스 + 브라우저 새 창

**개념**: 지금의 `docker-compose.yml` 구성 그 자체가 이미 "별도"다 — 포트(게이트웨이 8651, 대시보드 127.0.0.1:9128, mock-pos 8080)와 컨테이너명(`hermes-triagent-smb*`)이 형제 프로젝트와 겹치지 않도록 이미 분리돼 있다. 남은 작업은 이를 "MVP 제품"으로서 운영하기 편하게 다듬는 것 — 실행 스크립트, 헬스체크, 대시보드 인증 정리, 바로가기(브라우저 새 창으로 열기) 정도.

- **개발 범위**: 거의 없음. `.hermes/config.yaml`의 `dashboard.basic_auth` 운영용 비밀번호 교체, `docs/`에 "MVP 운영 가이드" 정리, 필요 시 `docker compose up -d` + URL을 여는 셸/배치 스크립트 1개 추가.
- **"창" 실현 방식**: 브라우저에서 `http://127.0.0.1:9128`을 새 창(또는 PWA로 설치 시 독립 창)으로 연다. Chrome/Edge는 `--app=http://127.0.0.1:9128` 플래그로 주소창 없는 앱 모드 창을 띄울 수 있어 추가 코드 없이 "별도 창처럼" 보이게 할 수 있다.
- **장점**: 리스크 최소, 이미 실측 검증된 구조 재사용([08-docker-deployment.md](08-docker-deployment.md) 실측 완료), 형제 프로젝트와 동일 패턴이라 유지보수 부담 낮음.
- **단점**: UI가 Hermes CLI 대시보드 그대로라 SMB 사장님 관점의 "주문 현황/재고 알림" 같은 업무 화면은 아니다. 커스터마이징 여지가 적음.
- **소요**: 반나절 이내.

### 옵션 B — 데스크톱 앱 창 (Electron/Tauri 래퍼)

**개념**: 옵션 A의 대시보드 URL(`http://127.0.0.1:9128`)을 감싸는 얇은 네이티브 데스크톱 앱을 새로 만들어, 브라우저가 아닌 독립 실행 파일(아이콘 더블클릭)로 실행되는 "진짜 별도 창"을 제공한다.

- **개발 범위**: 신규 컴포넌트 `desktop-app/` 추가 — Electron(`main.js`가 `BrowserWindow`로 대시보드 URL 로드) 또는 더 가벼운 Tauri. `docker compose up -d` 자동 실행/헬스체크 로직, 트레이 아이콘, 종료 시 컨테이너 정리 등 부가 기능 필요.
- **장점**: 데모/영업용으로 "제품처럼" 보임(taskbar 아이콘, 독립 창, 브라우저 주소창 없음). 로컬 Docker 상태를 앱이 감시/제어 가능.
- **단점**: 신규 기술 스택 도입(Node/Electron 빌드 체계), 유지보수 부담 증가, Hermes CLI 대시보드 자체의 UI 한계는 그대로(속을 바꾸는 게 아니라 액자만 새로 만드는 것).
- **소요**: 며칠 (Electron 셋업 + 패키징 + 아이콘/설치본 작업 포함 시 더 소요).

### 옵션 C — 경량 커스텀 웹 UI (SMB 맞춤 화면)

**개념**: Hermes 내장 대시보드 대신, SMB 사장님이 보기 편한 맞춤 화면(오늘의 주문 현황, 재고 부족 알림, 예약 캘린더, HITL 승인 대기 큐)을 새로 만들어 별도 서비스/포트로 띄운다. Mock POS API와 Hermes gateway API를 직접 호출하는 신규 백엔드+프론트엔드가 필요하다.

- **개발 범위**: 가장 큼. 신규 프론트엔드 프로젝트(React 등) + 백엔드(또는 mock-pos/Hermes gateway 직접 호출) + 인증 + HITL 승인 UI 신규 구현.
- **장점**: 실제 SMB 업무에 맞춘 MVP 화면 제공 가능, 장기적으로 제품화하기 가장 적합.
- **단점**: 개발 범위·기간이 압도적으로 큼, Hermes 프로필/HITL 로직과의 연동 지점을 새로 설계해야 함(현재 HITL은 Discord 승인 기반 — [06-hitl-approval-design.md](06-hitl-approval-design.md)), 유지보수 대상 급증.
- **소요**: 주 단위 이상.

## 비교 요약

| 항목 | A. 독립 배포 인스턴스 | B. 데스크톱 앱 창 | C. 커스텀 웹 UI |
|---|---|---|---|
| 신규 코드량 | 거의 없음 | 중간 (Electron 앱 1개) | 큼 (프론트+백엔드) |
| "별도 창"의 실체 | 브라우저 새 창/앱 모드 | 진짜 독립 실행 파일 | 브라우저 새 창(자체 UI) |
| 업무 화면 적합도 | 낮음 (CLI 대시보드 그대로) | 낮음 (그릇만 다름) | 높음 (맞춤 설계 가능) |
| 리스크 | 최소 | 중간 | 높음 |
| 소요 기간 | 반나절 | 며칠 | 주 단위 |
| 기존 검증 자산 재사용 | 100% | 100%(속) | 부분적 |

## 추천

**옵션 A를 먼저 "MVP"로 확정하고, 필요하면 옵션 B(앱 모드/Electron)를 다음 단계로 얹는 순서**를 추천한다. 이유:

1. 이미 실측 배포 검증이 끝난 구조([08-docker-deployment.md](08-docker-deployment.md) "검증 완료" 항목)를 그대로 재사용해 리스크가 없다.
2. "별도 창"이라는 요구는 브라우저 앱 모드(`--app=` 플래그)만으로도 최소 비용에 충족된다.
3. 옵션 C(커스텀 업무 화면)는 방향성 자체는 좋지만 별도의 큰 프로젝트이므로, MVP 단계에서 바로 착수하기보다 옵션 A로 먼저 운영해보고 실제로 어떤 화면이 부족한지 확인한 뒤 착수하는 것이 낭비가 적다.

## 실행 시 검증 방법 (옵션 A 기준)

1. `docker compose ps`로 3개 컨테이너(`hermes-triagent-smb`, `-dashboard`, `-mock-pos`)가 모두 떠 있는지 확인.
2. `curl http://127.0.0.1:9128/` 302(로그인 리다이렉트) 확인 — "Up"만으로는 내부 크래시 루프를 못 잡는다는 기존 함정 기록 참고([08-docker-deployment.md](08-docker-deployment.md) 하단).
3. 브라우저에서 `http://127.0.0.1:9128`을 새 창(또는 `--app=` 앱 모드)으로 열어 로그인 및 코디네이터 대화까지 실제로 확인.
4. `docker compose exec hermes hermes doctor`로 7개 프로필 인식 확인.
