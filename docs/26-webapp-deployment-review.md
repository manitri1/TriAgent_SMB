> 검토일: 2026-09-12. 이 저장소(`/opt/smb`)의 실제 VPS 배포 상태를 직접 실측(컨테이너
> 상태, health check, pytest 실행)하고 기존 문서(`02`, `06`, `07`, `08`, `14`, `19`, `20`,
> `22`장)를 근거로 정리했습니다. "배포 가능한가"와 "(실제 매장 운영에) 활용 가능한가"를
> 구분해서 봅니다 — **결론부터 말하면 배포는 이미 완료되어 안정적으로 돌고 있지만,
> 실 매장 운영을 이 웹앱으로 완전히 대체하기에는 아직 이르고 데모/파일럿 단계입니다.**

## 2. 현재 배포 상태 (실측)

VPS(`srv1923951`, Hostinger)에서 `docker compose ps` 결과 4개 컨테이너 모두 정상 기동 중:

| 컨테이너 | 역할 | 포트(호스트→내부) | 상태 |
|---|---|---|---|
| `hermes-triagent-smb` | Hermes 게이트웨이(7개 에이전트) | `18651→8642` | Up 21h |
| `hermes-triagent-smb-dashboard` | Hermes 범용 관리 대시보드 | `127.0.0.1:19128→9119` | Up 4d |
| `hermes-triagent-smb-mock-pos` | POS 시뮬레이터(FastAPI) | `18080→8080` | Up 3d |
| `hermes-triagent-smb-webapp` | **이 문서가 검토하는 웹앱** | `127.0.0.1:19131→8090` | Up 20h |

- `curl http://127.0.0.1:19131/health` → `200` (정상)
- `curl https://smb-webapp.srv1923951.hstgr.cloud/` → `401`(Basic Auth 정상 요구 — 예상된 동작)
- `cd webapp && pytest` → **51개 전부 통과**(`test_pages.py` 26, `test_hermes_client.py`/
  `test_agent_relay.py`/`test_auth.py`/`test_pos_proxy.py` 각 5)
- Traefik 라벨을 통해 **터널 없이 HTTPS로 상시 접속 가능**(`19·20장` 참고) — 이미
  운영 방식이 정해져 있고 검증됨.
- bind mount(`./.hermes:/opt/data`) 구조라 컨테이너를 지워도 파일 데이터는 VPS 디스크에
  남음 — 백업/복구 절차도 문서화됨(`20장` 4절).

**즉, "배포"라는 관점에서는 이미 끝난 상태이고 안정적으로 운영되고 있습니다.**

## 4. 배포 가능성 — 상세 근거

- **인증**: 앱 전체(화면+API)가 자체 scrypt 해시 기반 HTTP Basic Auth로 보호됨(`auth.py`).
  Hermes 대시보드 계정과 완전히 분리됨.
- **비밀 관리**: `MOCK_POS_API_KEY`, `WEBAPP_BASIC_AUTH_PASSWORD_HASH` 등은 전부 환경변수
  주입(`config.py`)이며 하드코딩 없음. 저장소 루트 `.env`는 gitignore 대상.
- **쓰기 경로 통제**: 브라우저 JS는 mock-pos의 쓰기 엔드포인트를 절대 직접 호출하지 않고,
  모든 쓰기는 `coordinator`를 거쳐 가격/재고 검증과 HITL 게이트를 통과함
  (`test_pos_proxy.py::test_pos_proxy_never_registers_a_write_route`로 구조적으로 고정).
- **네트워크 노출**: `127.0.0.1` 전용 바인딩 + Traefik 라벨 조합으로, 직접 포트 노출 없이
  HTTPS 서브도메인으로만 외부 접근 가능(`19·20장`).
- **재기동 복원력**: `restart: unless-stopped` + systemd docker 자동 기동 — VPS 재부팅 시
  사람 개입 없이 자동 복구(`20장` 5절).

이 부분만 보면 **소규모 프로덕션 배포로도 무리가 없는 수준**입니다.

## 5. 실사용(활용) 가능성 — 갭과 리스크

| # | 갭/리스크 | 심각도 | 설명 |
|---|---|---|---|
| 1 | **Mock POS는 실제 POS/결제 게이트웨이가 아님** | 🔴 Critical | 인메모리 저장소라 컨테이너 재시작 시 주문·재고·매출이 전부 초기화됨(`14장` 3.1절). 실 매출을 이 시스템 하나로 관리할 수 없음 — **실사용 전환의 최대 전제조건은 실제 POS/결제 연동** |
| 2 | **응답 지연 25초~4분** | 🟠 High | 쓰기 요청은 `coordinator` 위임을 거치므로 느림. 카운터 앞에서 손님을 기다리게 하는 실시간 접객에는 부적합 — 백오피스용(재고/예약/문의 회신)으로는 무리 없음 |
| 3 | **화면 5(예약)·6(라이브데모) 컨테이너 e2e 미검증** | 🟡 Medium | 단위 테스트만 통과, 실채팅→mock-pos 반영 확인 안 됨(`README.md` 빌드 상태) |
| 4 | **브라우저 시각 검증 미완료** | 🟡 Medium | 이 실행 환경이 headless라 Playwright 등으로 렌더링/반응형을 직접 확인하지 못함(`12장` §8-9와 동일 제약) |
| 5 | **webapp 컨테이너에 호스트 `docker.sock` 마운트** | 🔴 Critical(보안) | `hermes_client.py`가 Docker SDK `exec_run`으로 hermes 컨테이너를 제어하기 위해 필요하지만, webapp이 침해되면 **호스트 수준 Docker 전체 제어권**으로 이어질 수 있는 구조. `127.0.0.1` 전용 노출 + Basic Auth로 완화하고 있으나 알려진 트레이드오프로 문서화만 되어 있음(`README.md`) |
| 6 | **계정 체계 미성숙** | 🟡 Medium | 전 직원이 공용 `admin` 계정 1개를 공유. 직원별 권한 분리·감사로그(누가 언제 무엇을 했는지) 없음 |
| 7 | **HITL 승인 = "수동 집행 안내"에 그침** | 🟠 High | 프로모션 발송·대량 발주 확정·환불 승인 후에도 실제 집행은 여전히 사람이 수동으로 처리(`06장`) — "승인하면 자동으로 다 끝난다"는 기대와 다름, 실사용 시 이 경계를 명확히 안내해야 함 |
| 8 | **LLM API 크레딧 소진 시 조용한 실패** | 🟡 Medium | 크레딧이 없으면 1초 이내에 빈 응답/이상 응답이 오는데, 이를 감지·알림하는 모니터링이 없음(`14장` 트러블슈팅 표에서 실측 확인된 사례) |
| 9 | **단일 VPS, 이중화 없음** | 🟡 Medium | 인프라 장애 시 전체 서비스 중단. 소규모 매장 1곳 운영 규모에서는 감수 가능한 리스크일 수 있으나 인지는 필요 |
| 10 | **Discord 승인 대화 흐름 미검증** | ⚪ Low | `DISCORD_BOT_TOKEN` 미설정으로 사장님-에이전트 간 실제 원격 승인 대화는 아직 실측 안 됨(`07장`) |

## 6. 권장 로드맵

**지금 바로 가능한 활용 범위(추천)**
- 직원 교육·시연용 콘솔로 사용 (실제로 손님 문의 응대 연습, 재고/예약 워크플로 체험)
- 사장님이 원격에서 재고·예약·매출 현황을 확인하는 **읽기 전용 대시보드**로 활용
- 소규모 파일럿(예: 특정 요일에만, 실 결제와 분리된 "연습 주문"으로) 운영

**실사용 전환을 위해 필요한 작업 (우선순위순)**
1. 실제 POS/결제 게이트웨이 연동(가장 큰 블로커) — mock-pos를 대체하거나 실 시스템과
   동기화하는 어댑터 필요
2. 화면 5·6의 컨테이너 e2e 검증 + 브라우저 시각 QA(비-headless 환경에서 1회 필요)
3. 직원별 계정/권한 분리, 작업 감사로그
4. `docker.sock` 마운트를 대체할 최소권한 방식 검토(예: hermes 게이트웨이에 전용 내부
   API를 추가해 webapp이 Docker를 직접 다루지 않도록)
5. LLM 크레딧/오류에 대한 모니터링·알림(Slack/Discord 등)
6. 응답 지연 완화 — 비동기 알림(완료 시 푸시) 또는 진행 상태 폴링 UI로 체감 대기시간 개선

## 7. 결론

이 웹앱은 **아키텍처와 배포 파이프라인 자체는 검증을 마친 완성도 있는 시스템**입니다
(6화면 중 4개는 실컨테이너 e2e까지 확인됨, 인증·HTTPS·자동 재기동까지 갖춤). 다만 핵심
데이터 계층이 아직 시뮬레이터(mock-pos)이고, 보안·계정·모니터링 측면에서 실 운영에
필요한 몇 가지 장치가 빠져 있어 **"지금 당장 실제 매장 결제/재고를 이 시스템 하나로
전적으로 운영"하기보다는, 데모·교육·파일럿용으로 활용하면서 5절의 갭을 순차적으로
메우는 것을 권장**합니다.
