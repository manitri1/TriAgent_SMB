### STEP 1. 네 칸 채우기

화면 · 로직 · 데이터 · 배포 각 칸에 해당 내용 기재. 공란으로 남는 칸은 아직 미정인 영역.

| 층 | 정의 | 내용 |
|---|---|---|
| **화면** | 사용자가 보고 누르는 것 (목록, 입력창, 버튼, 결과 표시) | webapp 4화면 — 고객 문의 채팅 / 주문 접수(품목 선택 폼 + 자유채팅) / 재고 현황·재입고 요청 / 실시간 대시보드(Chart.js). 별도로 Hermes 범용 채팅 UI(`:19128`)도 병행 존재 |
| **로직** | 판단하고 계산하는 규칙 (조건 분기, 점수 계산, AI 호출) | coordinator의 위임 로직(`terminal` 동기 호출), 7개 프로필별 업무 로직(주문·결제 처리, 재고 임계치 판정, 예약 가능 시간 계산, 문의 분류·응답, 매출 집계, 캠페인 조건 판정), 3개 HITL 승인 게이트 판정(프로모션 집행 / 대량 발주 / 환불), OpenAI `gpt-5-mini` 호출 |
| **데이터** | 저장되어 남는 것 (사용자 정보, 기록, 업로드한 파일) | mock-pos DB(주문·결제·재고·매출 기록), 각 프로필 `state.db`(세션·메모리), `workspace/*.md` 카드(kanban 진행상황), 웹앱 대화 세션(`conversation_store.py`), `.env` 설정값 |
| **배포** | 다른 사람이 들어오는 통로 (도메인, 서버, 접속 환경) | Docker Compose 컨테이너(`hermes-triagent-smb*`, `mock-pos`, `webapp`), Traefik HTTPS 리버스 프록시, 포트(게이트웨이 18651 / 대시보드 19128 / webapp 19131), VPS 배포, HTTP Basic Auth 보호 |

**공란 여부**: 없음 — 네 층 모두 이미 실제로 정의·구현된 상태.

### STEP 2. 형태 확정하기

웹 · 앱 · 데스크탑 중 선택. 판단 기준은 핵심 가치의 '휴대폰 전용' 성립 여부.

| 항목 | 내용 |
|---|---|
| **선택** | 웹 |
| **선택 사유 (1줄)** | 사장님이 매장 PC/폰 브라우저로 주소만 열면 접속 가능하고, 카메라·푸시알림·위치 등 '휴대폰 전용' 기능이 핵심 가치가 아니므로 웹이 적합 |

---

### STEP 3. 유형 고르기

다섯 가지 화면 패턴(A 목록–상세형 / B 대시보드형 / C 흐름–결과형 / D 대화형 / E 제작도구형) 중 주 화면 유형 1개 선택. 두 유형에 걸칠 경우 주 화면 하나만 선택.

| 항목 | 내용 |
|---|---|
| **선택** | D. 대화형 (대화창·기록·내보내기 / AI 호출·대화 맥락 관리 / 대화기록·참조문서) |
| **선택 사유** | 재고·대시보드처럼 대시보드형(B) 요소도 존재하지만, 핵심 가치는 "사장님이 말을 걸면 coordinator가 알아듣고 하위 에이전트에게 위임해 처리한다"는 대화 기반 처리이며, 웹앱의 쓰기 작업(주문 생성·재입고)도 전부 채팅 위임 구조를 그대로 거침. 겸용 대신 대화형을 주 화면으로 확정 — 대시보드/재고 조회는 보조 화면으로 후순위 |

이 선택 결과(웹 · 대화형)는 이후 화면 설계·레퍼런스 단계에서 계속 사용.
