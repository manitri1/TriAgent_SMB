## 1. 비교 기준

- **기존 방식(이 앱이 없을 때)**: 사장님 1인이 카운터·발주·응대·마케팅·정산을 전화·수기 메모·개별 POS를 오가며 전부 직접 처리한다.
- **AI 에이전트 방식(이 앱이 있을 때)**: coordinator가 6개 전문 에이전트(주문/결제·재고·예약·고객문의·매출분석·마케팅/CRM)에게 위임해 하나의 콘솔에서 처리하고, **돈이 오가거나 손님에게 나가는 순간만** 사장님이 승인한다(HITL 게이트).

## 3. 정성적 분석 — 구조적으로 달라지는 것

- **의사결정 구조 전환**: "전부 다 확인"에서 "예외만 확인"으로 — 관리 대상이 12건에서 3건으로 줄지만, 결정권 자체는 그대로 사장님에게 남는다.
- **정보 유실 방지**: 전화 응대 중 놓치던 예약·문의가 콘솔에 기록으로 남아, "두 통을 그대로 놓침" 같은 손실이 줄어든다.
- **감정노동 분리**: 컴플레인 1차 응대(사과·재제조 안내)를 에이전트가 흡수하고, 민감한 건만 요약해 사장님에게 전달한다.
- **데이터 축적이 실제 제안으로 이어짐**: 대시보드에 쌓인 재방문·매출 데이터를 바탕으로 **마케팅·CRM 제안 팝업**(오늘 추가)이 VIP 감사, 이탈 위험 재유치, 판매 저조 품목 홍보, 인기 메뉴 세트 프로모션 4가지를 스스로 계산해 제시한다. 사장님은 팝업에서 하나를 골라 누르기만 하면 marketing-crm-agent가 문구 초안을 작성한다 — 타임라인에서 가장 취약했던 "마케팅 여력 부족"(등장 1회) 페인포인트를 가장 직접적으로 보강한 사례다.
- **신뢰 구조가 명시적**: 자동화가 전부가 아니라, 돈이 오가거나 손님에게 나가는 3곳만 HITL 게이트로 사람이 최종 확인한다 — "AI가 마음대로 결제·발주·홍보 집행을 하지 않는다"는 것을 화면에서 직접 확인할 수 있다.

## 5. 정직하게 밝히는 한계

- 전화·음성 응대는 여전히 사람이 수행한다 — 에이전트는 웹 콘솔·Discord로 들어온 **텍스트** 요청만 처리한다(음성 인식 기능 없음).
- 카카오톡은 실제로 연동되어 있지 않다 — 표기상 카카오톡 접점은 Discord·웹 콘솔로 대체 시연한다.
- 마케팅 문구는 승인 후에도 **사장님이 직접 게시**해야 한다(광고 플랫폼 자동 게시 연동 전 단계) — marketing-crm-agent는 애초에 발송 수단(messaging 툴)을 갖고 있지 않다.
- 가격정책·구독 수익 구조는 아직 설계 전이다.
- 05:30/21:00 같은 야간 자동 브리핑은 Hermes의 cron 기능으로 구현 가능하지만, 이 저장소에서는 아직 실제로 설정·검증되지 않았다.

## 6. 결론

같은 12개 접점을 기준으로, 이 앱은 사장님이 **매번 직접 개입해야 하는 지점을 100%에서 25%로 줄이면서도**, 돈이 오가거나 손님에게 나가는 결정에 대해서는 여전히 사람이 최종 승인하도록 설계돼 있다. 즉 "자동화"가 아니라 **"반복 노동의 위임 + 결정권의 유지"** 구조다. 오늘 추가된 마케팅·CRM 제안 기능은 그동안 가장 약했던 "마케팅 여력 부족" 페인포인트를 데이터 기반으로 직접 보강한 사례다.

**라이브 데모 반영 관련 참고**: 위 2번 표의 "기존 방식이었다면 이랬다"는 한 줄을 실제 `/live-demo` 화면의 각 장면 옆에 그대로 노출하면, 시연을 보는 사람이 도입 효과를 즉시 체감할 수 있다. 다만 이는 화면 코드를 수정하는 작업이라, 데모데이 준비 초안(`260913_마니카페_데모데이_준비_초안.md`)의 "멘토링 기간 중 신규 기능/디자인 전면 수정 금지" 방침과 겹칠 수 있어 실행 여부는 별도 확인 후 진행한다.
