## 02. 기능 분해와 MVP 범위

이번 범위에 남긴 5개, 잘라 낸 항목 — 원본과 동일한 선별 기준(핵심가치 성립 여부·기간 내 구현 가능·사람 손 대체 불가)을 유지하되, **진행 상태를 갱신**했다.

| # | 기능 | 9/5 상태 | 9/11 상태 |
|---|---|---|---|
| 1 | 주문 접수·결제 | 검증 완료 | 동일 + webapp `/orders` 화면에서 실제 "카푸치노 1잔" 주문 → mock-pos `COMPLETED` → 당일 매출 반영까지 e2e 확인(3분 39초) |
| 2 | 재고 파악·재입고 요청 | 검증 완료 | 동일. 읽기는 mock-pos 프록시 직결, 쓰기는 coordinator 위임 원칙 확정 |
| 3 | 고객 문의 응대 | 검증 완료 | webapp `/support` 화면에서 세션 연속성(`--resume`)까지 실제 컨테이너로 확인 |
| 4 | 실시간 매출·재고 대시보드 | 검증 완료 | webapp `/dashboard` 화면에서 Chart.js 렌더링 + 화면2 주문 반영까지 확인 |
| 5 | 승인 게이트 3종 | 검증 완료 | 동일. 발주 상한은 마니카페 연남점 실제 운영값인 **15만원**으로 확정([07-roadmap.md](../docs/07-roadmap.md)) |

제외 대상(잘라 낸 기능)도 원본과 동일하되, [260911_TriAgent_SMB_확장기능_검토.md](260911_TriAgent_SMB_확장기능_검토.md)에서 더 세분화한 우선순위를 참고할 것 — 특히 "Discord 실제 알림 발송"과 "3개 프로필 단독 스모크 테스트"는 다른 항목보다 소요가 작아 우선 착수를 권장한다.

**점검**: 남긴 5개 기능만으로 "마니카페 사장님이 주문·재고·문의·승인을 한 창구에서 처리한다"는 한 문장 설명이 원본과 동일하게 유지된다 — 선별 통과.

## 03. 사용자 시나리오와 화면 흐름

원본의 4화면 흐름(`/support` → `/orders` → `/inventory` → `/dashboard`)과 분기 로직(재고 부족 시 승인 대기 전환)은 변경 없음. **갱신 사항**: 이 흐름 전체가 이제 "설계"가 아니라 "실측 검증된 동작"이다 — [webapp/README.md](../webapp/README.md) "빌드 상태" 절 참고.

---

## 04. 화면이 아닌 승인 흐름의 규칙

3개 HITL 게이트(프로모션 집행 / 대량 발주 15만원 상한 / 결제 환불)와 Active Verification 원칙 — **변경 없음**, 원본 그대로 유효.

## 08. 결론

원본 MVP 기획서(9/5)의 구조·범위 판단은 그대로 유효하다. 가장 큰 변화는 **"계획"이었던 항목 다수가 "완료"로 넘어갔다는 것**(webapp e2e 검증, Traefik HTTPS, 인증 정보 이전)이다. 다음 6일(9/12~9/17 상당 기간)의 우선순위는 원본 계획표보다 **Discord 알림 검증과 3개 미실행 프로필의 단독 스모크 테스트**를 앞당기는 것을 권장한다 — 둘 다 새 기능 개발이 아니라 "이미 설계된 것의 실제 확인"이라 소요 대비 리스크 감소 효과가 크다.
